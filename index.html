detectron2 两种压缩方法的对比：压缩写法压得更小，nanolize 重写更快、行为保持得更完整

同一份 detectron2，两种方法各自压出一个更小的版本。这一页把两个结果放在一起比：用了多久、花了多少钱、同一口径下体积降到多少，以及同一套 268 条行为检查和 91 个能力的验证各过了多少。

要点

  • 压缩写法的体积更小。源码加配置合计是原版的 61.3%，nanolize 重写是 74.9%。只看 Python 源码那部分，是 57.3% 对 63.7%。
  • 差距有一半来自 nanolize 没有碰的文件。nanolize 这次把 224 个文件原样带走（C++/CUDA 源码、YAML 配置、LVIS 类别表），压缩写法把其中的 YAML 压成一行、把类别表放进了 gzip。
  • nanolize 重写更快，花费相同。7 小时 37 分对 12 小时 28 分，都是 570 多美元。
  • 行为上 nanolize 重写全部通过，压缩写法 268 条里有 4 条没过。4 条里有 1 条是实际的功能退化：一个原本能独立运行的数据集准备脚本，现在没装 detectron2 就跑不起来。另外 3 条是配置文件的文本和结构变了。
  • 这套检查是 nanolize 那次运行冻结的，对它有主场优势。nanolize 的第一版只过了 127 条，修了三轮才全过；压缩写法从没见过这些检查，第一次跑就过了 264 条。
  • 两种方法的目标不同。nanolize 按功能重写，交出的是正常可读的代码；压缩写法保留原来的文件和逻辑，把写法压到最短，代码不是给人读的。见两种方法做了什么。

两种方法做了什么

两边的起点是同一个原版，做的事很不一样。下面的名字是这一页起的：一个叫“nanolize 重写”，一个叫“压缩写法”。

nanolize 重写压缩写法
做法先画出功能图，冻结一套行为检查，再让作者会话对照约定重新写一遍代码，和原版比较，不过就修保留原来的文件和逻辑，把写法压到最短
Python 代码正常的缩进、命名和文档字符串；代码对照约定重新写过，比原版短一格缩进，多条语句用分号连成一行，局部变量改成单字母，注释和文档字符串全部删掉
文件结构按功能重新组织：450 个源文件变成 399 个（去掉 59 个，新增 8 个）和原版相同，只新增了 72 个文件（公共配置和数据表），去掉 1 个
YAML 配置原样带走，一个字节不改每个文件压成一行，公共部分抽成 64 个 Base-N 文件
大的数据表LVIS 类别表、COCO 类别、模型库地址表等LVIS 类别表原样带走；其余留在代码里从代码里挪出来，放进 3 个 gzip 文件，运行时解压读取
C++/CUDA 源码原样带走18 个文件全部做了压缩
文档不在交付范围里保留并压缩到原来的 30%
源码行数原版 71,975 行48,695 行15,993 行（语句连成了一行，行数不可比）

同一段代码，三个版本

取配置模块里相邻的两个函数：原版、nanolize 重写、压缩写法。

原版
def get_cfg() -> CfgNode:
    """
    Get a copy of the default config.

    Returns:
        a detectron2 CfgNode instance.
    """
    from .defaults import _C

    return _C.clone()


def set_global_cfg(cfg: CfgNode) -> None:
    """
    Let the global config point to the given cfg.

    Assume that the given "cfg" has the key "KEY", after calling
    `set_global_cfg(cfg)`, the key can be accessed by:
    ::
        from detectron2.config import global_cfg
        print(global_cfg.KEY)

    （后面还有 3 行说明）
    """
    global global_cfg
    global_cfg.clear()
    global_cfg.update(cfg)
nanolize 重写
def get_cfg() -> CfgNode:
    from .defaults import _C

    return _C.clone()


def set_global_cfg(cfg: CfgNode) -> None:
    """Fills `global_cfg` with the content of cfg."""
    global_cfg.clear()
    global_cfg.update(cfg)
压缩写法
def get_cfg():from.defaults import _C; return _C.clone()

def set_global_cfg(cfg): global global_cfg; global_cfg.clear(); global_cfg.update(cfg)

这一段比较短，两边都很省。差别在长函数里更明显：nanolize 重写会改结构，压缩写法只改写法。nanolize 交付的代码里，参与比较的函数行有 62% 和原版相同。

读这些数字时要知道的

  • 检查对 nanolize 有主场优势。268 条是 nanolize 那次运行冻结的，它交付的版本就是对着这些检查修到全过的。压缩写法没有见过它们。所以“268 对 264”不能读成 nanolize 的方法更能保持行为；更公平的读法是：压缩写法第一次跑就过了 98.5%，nanolize 的第一版是 47%。
  • 反过来的比较没有做。没有拿压缩写法自带的测试去跑 nanolize 的版本。nanolize 是重写，内部结构变了，和内部结构绑定的原版测试本来就不适用。它自己在交付后回放过 73 个离开验收的原版测试：原版通过 68 个，交付的版本通过 67 个。
  • 两种方法的目标不同，这一页没有量可读性。nanolize 交出的是可以继续维护的代码；压缩写法交出的代码一格缩进、单字母变量、没有注释，更像一份发布用的压缩包。只比体积，对前者不利；只比行为，对后者不利。
  • 压缩写法改过的 C++ 源码没有被验证。检查用的是原版源码编译出的扩展，见行为检查一节。
  • 两边都没有安装检查。没有在全新环境里把任何一个版本装起来过。nanolize 的交付因此带着“没有安装证据”的缺口；压缩写法同样没有这项证据。
  • 压缩写法的用时和花费不是这里量的。由它的操作者提供，这一页没有它的运行记录。
  • 没有比运行速度。压缩写法在导入时要解压数据表，这一页没有量它对启动时间的影响。
  • 压缩写法把项目目录里的测试文件也压缩了。DensePose 和 TensorMask 两个项目下的测试文件和原版不同。这些文件不在 268 条检查里，不影响上面的结果；nanolize 的验证命令会把它报成“原版测试被改过”。
